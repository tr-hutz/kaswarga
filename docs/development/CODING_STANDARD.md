---

# 1. Purpose

This document defines the coding standards for the KasWarga project.

The goals are:

- Maintain consistency
- Improve readability
- Simplify maintenance
- Reduce technical debt
- Support AI-assisted development
- Enable easier onboarding for future developers

All contributors should follow this document.

---

# 2. General Principles

Always write code for humans first.

Readable code is preferred over clever code.

Avoid unnecessary abstractions.

Prefer explicit code over implicit behavior.

Every file should have a single responsibility.

---

# 3. Language Convention

## Source Code

All source code MUST be written in English.

Includes:

- Folder names
- File names
- Variables
- Functions
- Types
- Interfaces
- Enums
- SQL tables
- SQL columns
- Comments
- Commit messages

---

## User Interface

Default language:

Indonesian

Future localization should use i18n.

Never hardcode business strings inside services.

---

# 4. Naming Convention

## Variables

Use camelCase.

Good

```ts
resident
payment
totalAmount
currentBalance
```

Bad

```ts
Resident
TOTAL
jumlahBayar
```

---

## Functions

Use verb + noun.

Good

```ts
createPayment()

approvePayment()

rejectPayment()

sendNotification()

calculateBalance()
```

Avoid

```ts
payment()

data()

test()
```

---

## Boolean

Use prefixes.

```ts
isLoading

isApproved

hasPermission

canDelete

shouldNotify
```

---

## Components

Use PascalCase.

```tsx
PaymentTable

PaymentToolbar

ResidentForm

DashboardCard
```

One component per file.

---

## Hooks

Prefix with use.

```ts
usePayments()

useResidents()

useNotifications()
```

Hooks should only manage UI state.

---

## Types

Use PascalCase.

```ts
Payment

Resident

LedgerEntry

Notification
```

---

## Enums

Use UPPER_SNAKE_CASE.

```ts
PENDING

APPROVED

REJECTED

PAID

UNPAID
```

---

# 5. Folder Structure

Use Feature-First Architecture.

```
features/

payment/

resident/

expense/

ledger/

notification/

activity/
```

Each feature should contain only its own files.

---

Recommended structure

```
payment/

components/

hooks/

services/

repositories/

types/

constants/

utils/

validators/
```

---

# 6. Component Rules

Components are responsible only for rendering UI.

Components MUST NOT

- query database
- call Supabase directly
- contain business rules

Components SHOULD

- receive props
- render UI
- emit events

---

# 7. Hook Rules

Hooks manage UI logic.

Allowed

- loading state
- search
- pagination
- sorting
- filtering

Not allowed

Business validation

Database queries

Permission logic

---

# 8. Service Layer

Business rules belong here.

Examples

Approve Payment

↓

Create Ledger Entry

↓

Create Notification

↓

Create Activity Log

Service may call multiple repositories.

---

# 9. Repository Layer

Repository is the only layer allowed to access Supabase.

Responsibilities

- SELECT
- INSERT
- UPDATE
- DELETE

Repository should never

- send emails
- create notifications
- validate business rules

---

# 10. Server Actions

Use Server Actions whenever appropriate.

Business logic still belongs inside Services.

Server Action should orchestrate the request only.

---

# 11. Database Access

Never access Supabase directly inside

- Components
- Hooks

Always use

Repository

↓

Service

↓

Hook

↓

Component

---

# 12. Error Handling

Never ignore exceptions.

Always return predictable errors.

Example

```ts
{
    success: false,
    message: "...",
    errors: []
}
```

Never expose internal database errors.

---

# 13. Logging

Important business actions must create Activity Logs.

Examples

- Payment approval

- Expense creation

- Resident registration

- RT approval

---

# 14. Notification

Notifications should be generated by Services.

Never inside Components.

---

# 15. Validation

Validation should happen

Client

↓

Server

↓

Database

Never trust client input.

---

# 16. Constants

Avoid magic values.

Good

```ts
MAX_UPLOAD_SIZE
```

Bad

```ts
10485760
```

---

# 17. Utility Functions

Shared helper functions belong in

```
lib/utils
```

Feature-specific helpers belong inside the feature.

---

# 18. Comments

Explain WHY.

Do not explain WHAT.

Good

```ts
// Ledger must always be created
// after payment approval.
```

Bad

```ts
// Increment i
i++
```

---

# 19. Imports

Import order

1 React

2 Next.js

3 Third-party

4 Lib

5 Features

6 Components

7 Relative imports

---

# 20. Tailwind CSS

Prefer utility classes.

Avoid inline styles.

Group classes logically.

Example

```
Layout

Spacing

Typography

Color

Effects

State
```

Example

```tsx
className="
flex
items-center
justify-between
p-4
rounded-xl
bg-white
hover:bg-slate-50
"
```

---

# 21. Forms

Use controlled components.

Validation should display user-friendly messages.

Never expose raw database errors.

---

# 22. State Management

Prefer React state.

Avoid global state unless necessary.

Current recommendation

React Hooks

Future

React Context

Avoid Redux unless justified.

---

# 23. API Response

Always return predictable structure.

```ts
{
    success,
    message,
    data,
    errors
}
```

---

# 24. Activity Log

Every important business action must generate an activity log.

Actions should use predefined enums.

Never hardcode action strings.

---

# 25. Security

Never expose

- API Keys
- Service Keys
- Secrets

Use environment variables.

---

# 26. Performance

Avoid unnecessary re-rendering.

Memoize expensive calculations.

Use pagination.

Lazy load large modules.

---

# 28. Git Convention

Use Conventional Commits.

Examples

```
feat(payment): add payment approval

fix(ledger): prevent duplicate entries

refactor(notification): simplify service

docs: update coding standard

test(payment): add approval tests
```

# 29. Pull Request Checklist

Before merging

✓ Build succeeds

✓ No ESLint errors

✓ No TypeScript errors

✓ No console.log()

✓ Activity Log updated

✓ Notification updated

✓ Documentation updated

# 30. AI-Assisted Development

KasWarga is designed to support AI-assisted development.

When using AI

Always

- follow feature structure
- follow naming convention
- reuse existing services
- reuse repositories
- reuse UI components

Never

- duplicate business logic
- bypass repositories
- invent new naming conventions
- mix Indonesian and English in source code
