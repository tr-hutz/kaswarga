>
> Version: 1.0

---

# 1. Purpose

This document defines database design standards for the KasWarga project.

The goals are:

- Maintain consistency
- Improve readability
- Simplify migrations
- Support scalability
- Ensure data integrity
- Support Row Level Security (RLS)

Every new table must follow this convention.

---

# 2. Database Engine

Database Provider

Supabase PostgreSQL

All business data is stored inside PostgreSQL.

Authentication uses Supabase Auth.

Files are stored in Supabase Storage.

---

# 3. General Principles

Database is the source of truth.

Never duplicate business data.

Avoid storing calculated values unless necessary.

Normalize first.

Denormalize only after performance analysis.

---

# 4. Naming Convention

## Tables

Use

plural snake_case

Examples

```
users

roles

memberships

residents

payments

payment_details

expenses

ledger_entries

notifications

activity_logs

rt_registrations

resident_registrations
```

Never

```
Payment

tbl_payment

paymentData
```

---

## Columns

Use

snake_case

Examples

```
resident_id

created_at

updated_at

phone_number

house_number

payment_status
```

---

## Primary Key

Every table must use

```
id UUID PRIMARY KEY
```

UUID should be generated by PostgreSQL.

---

## Foreign Keys

Always use

```
resident_id

payment_id

rt_id

user_id

role_id
```

Never

```
id_resident

residentID

ResidentId
```

---

# 5. Standard Audit Columns

Every business table should contain

```
created_at

created_by

updated_at

updated_by
```

Optional

```
deleted_at

deleted_by
```

for soft delete.

---

# 6. Multi-Tenant Rule

Every business table MUST contain

```
rt_id
```

except

Global tables

Examples

```
roles

permissions

system_settings
```

---

# 7. Boolean Columns

Always prefix with

```
is_

has_

can_
```

Examples

```
is_active

is_verified

has_paid
```

---

# 8. Enum Columns

Prefer PostgreSQL ENUM.

Examples

Payment Status

```
PENDING

APPROVED

REJECTED
```

Registration Status

```
PENDING

APPROVED

REJECTED

EXPIRED
```

Notification Status

```
UNREAD

READ
```

---

# 9. Monetary Values

Never use FLOAT.

Use

NUMERIC

or

BIGINT

Recommendation

Store currency in whole Rupiah.

Examples

```
100000

250000

1500000
```

Never

```
100000.50
```

---

# 10. Date & Time

Always use

TIMESTAMPTZ

Store all timestamps in UTC.

Display according to user timezone.

---

# 11. File Storage

Files should never be stored inside PostgreSQL.

Only store

```
storage_path

file_name

mime_type

file_size
```

Actual files belong in Supabase Storage.

---

# 12. Index Strategy

Create indexes for

Foreign Keys

Frequently searched fields

Sorting fields

Examples

```
resident_id

rt_id

status

created_at

email
```

Composite indexes should be created only after query analysis.

---

# 13. Constraints

Use constraints whenever possible.

Examples

Unique

```
email
```

Check

```
amount > 0
```

Foreign Keys

NOT NULL

---

# 14. Soft Delete

Recommended.

Instead of deleting records

```
deleted_at

deleted_by
```

Queries should ignore deleted records by default.

---

# 15. Activity Log

Every important business action should create

activity_logs

The table should contain

```
actor_id

target_type

target_id

action

metadata

created_at
```

Metadata should use JSONB.

---

# 16. Notification

Notifications should contain

```
user_id

title

message

is_read

created_at

read_at
```

Future

```
channel

priority

email_sent_at
```

---

# 17. Ledger

Ledger must be append-only.

Existing ledger entries should never be modified.

Corrections should be made using adjustment entries.

---

# 18. Payment

Payment approval should be immutable.

Approved payments should not be edited.

Changes require

Reversal

or

Adjustment

---

# 19. Registration

Registration tables should store

Applicant Data

Approval Status

Approval Timestamp

Approver

Activation Token

Expiration

---

# 20. Membership

Membership connects

User

↓

RT

↓

Role

Users may belong to multiple RTs in future versions.

---

# 21. Row Level Security (RLS)

Every business table must enable RLS.

Policies should be based on

```
auth.uid()

↓

membership

↓

rt_id

↓

permission
```

Never trust client-side filtering.

---

# 22. Transactions

The following operations must be atomic

Approve Payment

Approve RT Registration

Approve Resident Registration

Create Expense

Ledger Adjustment

If one step fails

Rollback everything.

---

# 23. Migration Rules

Never modify an old migration.

Always create a new migration.

Migration filenames should follow

```
YYYYMMDDHHMM_description.sql
```

Example

```
202607061430_create_payments.sql
```

---

# 24. Seed Data

Seed files should include only

Roles

Permissions

Demo Data

Never include production data.

---

# 25. Backup Strategy

Recommended

Daily automatic backup

Weekly verification

Monthly restore testing

---

# 26. Performance Guidelines

Avoid SELECT *

Select only required columns.

Always paginate large datasets.

Review slow queries regularly.

# 28. Final Principles

Consistency is more important than optimization.

Data integrity is more important than convenience.

The database should enforce business rules whenever possible.

Every new table must comply with this document.
